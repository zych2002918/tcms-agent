## 1. 开场 60 秒 STAR 叙事（背熟）

**情境（Situation）**：列车 TCMS 的 CAN 网络承载安全攸关控制——紧急制动、门联锁、
超速防护一旦失效就是人身事故。真实列控验证有三个痛点：时序敏感（报文 50/100/500ms
周期，丢一帧都可能要命）、故障注入危险（在真车上模拟短路/超速不现实）、回归成本高
（安全逻辑一改就要重跑全部场景）。

**任务（Task）**：从零构建一个**无硬件依赖、可复现、覆盖率可度量**的开源测试平台，
系统性验证紧急制动、门联锁、ATP 速度监督等安全逻辑在正常与故障注入下的行为。

**行动（Action）**：
- 定义 22 帧报文 DBC 协议（116 信号）与编解码层，作为"列车的语言字典"；
- python-can 虚拟总线搭建多节点仿真（VCU/BCU/BMS），支持节点失活与故障注入；
- 实现 SIL2/SIL4 双通道表决的紧急制动管理（EBM）、独立于网络的 EBR 硬线回路、
  执行反馈三重证据、ISO 11898-1 错误状态机、ATP 三级监督与看门狗；
- 以虚拟时间基驱动 .asc 日志回放链与 YAML 故障场景 DSL，让故障全程可复现可审计。

**结果（Result）**：960 个自动化测试用例按预期通过（959 passed + 1 hardware skip），
关键报文（心跳、超速报警、制动指令）收发零丢失；代码语句覆盖率 97.96%，CI 全绿。
一条命令可演示全部 9 步仿真场景，支持回放真实 CAN 日志做回归，可作为 HIL 测试台架的基础设施。

> **HR 版**（把技术词换成"人话"）：我在电脑里完整仿真了列车控制系统，虚拟出几个
> 车载设备实时收发报文。跑通了三类安全场景——危险来了会紧急制动、设备坏了能被发现、
> 刹车动作有三重确认。960 个验证场景按预期通过（959 passed + 1 hardware skip），一条命令就能演示全过程，还能回放
> 真实日志做回归。这个平台可以成为未来硬件在环测试台架的基础。

## 2. 项目全景：六层链路（可画图讲）

```
协议层   tcms.dbc（打包数据，22 报文+116 信号+周期） → tcms/protocol.py（编解码）
   ↓
总线层   python-can 虚拟总线 ←→ 真实 CAN（环境变量切换）→ bus/canlog/network
   ↓
仿真层   单节点/多节点仿真器 + 故障注入（simulator/multinode/faults）
   ↓
安全逻辑层 联锁 → EBM → EBR 硬线 → 执行反馈 → 错误状态机 → ATP → 看门狗
   ↓
网络与时间 多网段拓扑、虚拟时间基、故障生命周期、回放链
   ↓
验证层   pytest 960 用例 + 覆盖率门禁 97% + CI + Allure 报告
```

**核心叙事**：列车在"说什么"（协议层）→ 报文怎么"跑"（总线层）→ 谁在"发"（仿真层）
→ 收到后怎么"保命"（安全逻辑层）→ 怎么让它"可复现可审计"（网络与时间层）→
怎么证明"测够了"（验证层）。按这条链路讲，逻辑自洽。

## 3. 六大层面试话术（每层 3-5 句）

### 3.1 协议层
DBC 现为 22 帧 / 116 信号（基础 8 帧：心跳 0x100、车速 0x200、手柄 0x300、车门 0x400、
报警 0x500、受电弓 0x600、制动 0x700、能源 0x780；扩展 14 帧覆盖 HVAC/PIS/照明/烟火/
辅助变流/ATO/走行部/后门/网关/防滑/牵引变流/司控台/充电机 13 域，11 发送节点），
周期分级 25/50/100/250/500ms。DBC 定义信号位布局，如
`SpeedKmh 0|16@1+ (0.1,0)`：起始位 0、16 位小端无符号、缩放 0.1——原始值 1000 = 100 km/h。
协议层是"需求文档"，测试就是需求验收（test_protocol.py 验证 ID 唯一、周期、值域、枚举）。

### 3.2 总线层
python-can 虚拟总线接口与真实 CAN 卡（PCAN/socketcan）完全一致，`TCMS_BUS_INTERFACE`
环境变量切换——同一套用例两种执行环境，这是 HIL 的基础设施设计。canlog 解析 Vector .asc
真实日志，network 做多网段拓扑：网关是独立设备（监听→FIFO 缓冲→扫描周期→过滤转发），
不是同步透传，缓冲满溢出丢弃不阻塞发送方，足迹防环对标网桥 STP。

### 3.3 仿真层
单节点 `TCMSNodeSimulator` 按 DBC 周期自动发报文，可设车速/车门/手柄、发报警、注入丢报；
多节点 `MultiNodeSimulator` 模拟 VCU/BCU/BMS 三个 ECU，`disable_node()` 模拟断电——
节点失活 → 其报文消失，这是看门狗/丢报检测的故障源。faults 提供位级篡改（CRC8 校验、
flip_bit、corrupt_byte），FaultInjector 做结构化注入编排。

### 3.4 安全逻辑层（深水区，面试必问）
按"检测 → 决策 → 执行 → 反馈"闭环讲：

| 模块 | 一句话 | 关键设计点 |
|------|--------|-----------|
| 联锁 interlocks | 不合法就不动 | 门-车联锁（开门移动=违规，阈值 0.5km/h）、超速-制动、牵引-制动互锁、方向-速度、车门-站台 |
| EBM ebm | 决策大脑 | 8 原因×3 模式矩阵；SIL4 任一通道触发即制动（故障安全），SIL2 双通道一致才制动（防误报）；缓解闭环：零速+原因消失→手柄回零→按钮保持≥3s→IDLE |
| EBR ebr | 独立于网络的保命线 | 得电=缓解、失电=制动；双回路 2oo2，任一失电即制动，单断线只预警不损失制动能力 |
| 执行反馈 exec_feedback | 决策≠执行 | 三重证据：制动缸压力≥300kPa+EB 激活回执+牵引切除；2s 超时判故障；APPLIED 期间牵引恢复=立即故障 |
| 错误状态机 errstate | 物理层健康 | ISO 11898-1：TEC/REC→Error-Active/Passive/Bus-Off；Bus-Off 后 128 次空闲恢复；接收错误不触发 Bus-Off |
| ATP atp | 三级干预 | 警告/SBI/EBI 三级阈值+动态 EBI 曲线（对标 ETCS，距目标越近允许速度越窄） |
| 看门狗 watchdogs | 节点还活着吗 | 周期喂狗，连续 3 次丢失判离线，恢复需连续 2 次（防抖） |

### 3.4.5 SIL2/SIL4 深潜：面试最深水区（背熟）

**SIL 是什么？**
SIL（Safety Integrity Level，安全完整性等级）是功能安全标准（IEC 61508 起源，
铁路用 EN 50126/50128/50129）定义的安全功能可靠性等级，共 4 级。它衡量的不是
"功能正不正确"，而是"**该安全功能该动作时必须动作、不该误动作时不能乱动**"的概率。

| SIL 等级 | 每小时危险失效概率（PFH） | 大致含义 |
|---------|--------------------------|---------|
| SIL 1 | 10⁻⁶ ~ 10⁻⁵ | 允许偶尔失效（一般设备） |
| SIL 2 | 10⁻⁷ ~ 10⁻⁶ | 失效后果严重（ATO 故障类） |
| SIL 3 | 10⁻⁸ ~ 10⁻⁷ | 高要求场景 |
| SIL 4 | 10⁻⁹ ~ 10⁻⁸ | **列车安全功能最高等级**（超速防护、紧急制动） |

> 说人话：SIL4 要求"一百亿小时才允许失效一次"，SIL2 是"一千万小时一次"。
> 等级越高 → 系统必须越冗余、越经得起故障考验。

**怎么构成（体系层面）？** 一个安全功能达到 SIL4，不是靠"写对代码"，而是靠整个
开发过程保证：
1. **需求**：每条安全需求（SR）可追溯到实现与测试（本项目 safety_case.md 的 SR-01~52）；
2. **架构冗余**：双通道独立实现 + 表决（本项目 SIL4 用双通道"任一触发"）、
   执行路径独立于通信介质（本项目 EBR 硬线回路）；
3. **开发过程**：编码规范、静态分析、独立验证（本项目 ruff lint + 属性测试）；
4. **覆盖率证据**：按 SIL 等级要求不同的覆盖率指标——SIL4 通常要求 MC/DC 级覆盖
   （本项目诚实说明：语句覆盖 97.96%，MC/DC 是真实认证要求，演示级未做）。

**本项目怎么构成 SIL2/SIL4 分级？（实现层面，面试必背）**

EBM 的 8 个触发原因按**危险后果严重度**分成两档（REASONS 表实测），用**双通道表决**保证可靠性：

| 档位 | 原因（REASONS 表 sil 值） | 表决逻辑 | 为什么这么设计 |
|------|------|---------|---------------|
| **SIL4**（后果=碰撞/人身事故） | 超速 overspeed、门开 door_open、ATP 故障 atp_fault、障碍物 obstacle、维护开关 maintenance_sw、硬线丢失 hardwire_loss（sil=4） | 双通道 **任一**触发即制动（`a or b`） | **故障安全**：宁可错杀不可漏杀——漏判一次就是事故，误判最多是晚点 |
| **SIL2**（后果=运营中断） | ATO 故障 ato_fault、火灾 fire_alarm（sil=2） | 双通道 **一致**才制动（`a and b`） | **防误报**：误报会无故紧急制动、中断运营，所以要求双通道一致确认 |

> 附加细节（能答出来加分）：ATO 故障只在 FAM 全自动模式生效，动作是"紧急制动 + 降级到 CM"；
> 门开在 RM 受限模式豁免（司机人工确认）；atp_fault 动作是"紧急制动 + 降级到 RM"。

代码实现（ebm.py 的 channel_vote，与真实源码一致）：
```python
def channel_vote(self, reason, channel_a, channel_b):
    # 原因分级来自 REASONS 表：sil >= 4 即 SIL4
    if REASONS[reason]["sil"] >= 4:      # 超速/ATP故障/门开 → SIL4
        return channel_a or channel_b    # 任一触发即制动（故障安全）
    if channel_a != channel_b:
        self._vote_mismatches += 1       # 两通道不一致 → 累计诊断计数
    return channel_a and channel_b       # SIL2：双通道一致才制动（防误报）
```

**面试怎么答（三段式）**：
> "SIL 是功能安全等级，衡量安全功能失效概率。本项目把 EBM 的 8 个原因按后果分级：
> 超速、ATP 故障这类**漏判=事故**的原因按 SIL4 处理，双通道任一触发就制动，宁错杀不放过；
> ATO 故障这类**误报=停运**的原因按 SIL2 处理，双通道一致才制动，防误报。
> 等级不是嘴上说的——每条需求都有实现、测试和覆盖率证据，这是 safety_case.md
> 里需求→实现→测试的映射，也是我说'SIL 是映射出来的，不是标上去的'的含义。"

**加分细节**：真实 SIL4 系统还会配 2oo3 表决（三个通道取多数，本项目 voting.py 实现）、
执行路径独立于网络（EBR 硬线）、执行反馈三重证据——这些都是在把"SIL4 的可靠性"
从口号变成工程手段。

---

### 3.5 网络与时间
- **虚拟时间基（timebase）**：virtual 模式 advance()/set() 确定性推进，替代 time.monotonic。
  测试要可复现，可复现要确定性时间——回放链/故障场景/看门狗全部注入虚拟时钟。
- **故障生命周期（faultlife）**：注入→传播→告警→恢复→归档五阶段，全程写入事件记录器
  （黑匣子），故障从发生到消失可审计。
- **场景 DSL（scenarios）**：故障场景写成 YAML，测试/演示人员无需改代码。
- **回放链（replay）**：.asc 日志→虚拟时钟→联锁/ATP/看门狗/EBM 全链路→告警断言，
  事故复盘工具。

测试金字塔：单元（test_ebm 8 原因×3 模式穷举）→ 集成（test_replay 全链路）→

## 4. 高频追问 Q&A

### HR 级（不问技术）
**Q：这项目是你一个人做的吗？**
A：是的，从协议定义到测试证据链完整独立完成。这正好证明我能从 0 到 1 把一条
完整链路落地——定义需求、设计协议、实现逻辑、写测试、上 CI、写文档。

**Q：为什么做这个项目？**
A：两个动机。一是列车控制是安全攸关系统，验证手段却长期依赖昂贵商业工具和人工；
二是我想证明自己理解从"报文怎么编码"到"安全逻辑怎么决策"的每一个环节，
而最好的证明方式就是用代码和测试把它落地。

**Q：项目最大的难点是什么？怎么解决的？**
A：最难的是"怎么让安全逻辑的测试既真实又可复现"。真实列控是实时系统，测试靠真车
既不安全也不现实。我的解法是三层：虚拟总线让报文流转真实发生；虚拟时间基让时间
确定性可推进；故障场景 DSL 让故障注入声明式、可审计。三者叠加，就把"真实列车测试"
变成"确定性可复现的仿真测试"。

**Q：如果让你重做一遍，会改什么？**
A：两个方向。一是接入真实硬件（PCAN/周立功）做 HIL 联调——接口层已就绪，环境变量
切换即可，这是最自然的下一步；二是对安全逻辑做形式化验证（如 TLA+）与覆盖率的
MC/DC 级分析，让证据链更接近真实 SIL 认证要求。

### 技术级（深水区）
**Q：EBM 为什么分 SIL2/SIL4？双通道表决怎么实现？**
A：SIL4 原因（超速/ATP 故障/门开）一旦误判漏判就是灾难，所以双通道任一触发即制动——
故障安全，宁可错杀；SIL2 原因（ATO 故障/火灾）误报会中断运营，所以双通道一致才制动，
防误报。实现上 `channel_vote(reason, a, b)`：SIL4 用 `a or b`，SIL2 用 `a and b`，
不一致时累计 vote_mismatches 并告警。

**Q：缓解闭环为什么这么设计？**
A：紧急制动一旦缓解错就是事故，所以设计成四步不可跳过的闭环：①速度 ≤0.5km/h
（零速）且 speed_valid 为真（速度信号可信）；②触发原因消失；③手柄回零位；
④缓解按钮保持 ≥3s。任何一步不满足都不能缓解，这是"故障安全 + 防误操作"的叠加。

**Q：EBR 和 EBM 有什么区别？**
A：EBM 是逻辑层的决策（在 CAN 上发指令），EBR 是物理层的执行（硬线回路，得电=缓解、
失电=制动）。EBR 存在的原因是 CAN 网络本身可能故障（Bus-Off/断线）——SIL4 执行路径
必须独立于通信介质。双回路 2oo2：任一失电即制动，单断线只预警不损失制动能力。

**Q：执行反馈为什么要三重证据？**
A：因为"决策≠执行"——EBM 发了制动请求不代表车真的在制动。三重证据是制动缸压力
≥300kPa（液压真实建立）+ EB 激活回执（执行器确认）+ 牵引切除联锁（动力已切断）。
任一缺失 2s 超时判执行层故障；最危险的是 APPLIED 期间牵引恢复（边制动边牵引），
立即判故障。

**Q：错误状态机 Bus-Off 后怎么恢复？**
A：ISO 11898-1 规定：TEC≥256 进入 Bus-Off，需 128 次总线空闲（11 个隐性位）后 TEC
清零才回到 Error-Active，恢复后还要 8 位发送退避。接收错误只加 REC，不触发 Bus-Off。

**Q：覆盖率 97.96% 差在哪？为什么不是 100%？**
A：54 条语句未覆盖，全是刻意保留的防御分支——比如 EBM 自愈超限转 FAULT、执行反馈
超时路径等"不该发生"的代码。硬凑 100% 会让测试失去区分度；诚实交代每一条未覆盖
分支的原因，比虚标更有说服力。CI 门禁 97% 保证不会回归。

**Q：虚拟时间基和真实时间怎么协调？**
A：`VirtualClock` 有 monotonic（真实时间偏移）和 virtual（advance()/set() 确定性推进）
两种模式。业务逻辑全部注入时钟对象（依赖注入），测试用 virtual 模式确定性驱动，
生产/演示用 monotonic。全局单例 `global_clock()` 提供统一时间源，可 install() 替换。

**Q：网关为什么要异步缓冲，不能直接转发吗？**
A：真实网关是独立设备：监听源网段→报文进接收缓冲 FIFO→按扫描周期处理→过滤表判定
转发/丢弃。直接转发是理想化模型，丢失了三个现实语义：转发时延（latency）、缓冲溢出
（满则丢新帧，不阻塞发送方）、足迹防环（帧不重复过同一网关）。异步模型下转发路径
可统计可审计（forwarded/dropped/overflow/buffered）。

**Q：为什么看门狗恢复要连续 2 次喂狗，而丢失要 3 次？**
A：防抖。3 次丢失才判离线，容忍单帧抖动；2 次连续喂狗才回在线，防止节点刚恢复
又立刻判活。不对称设计是工程惯例——判死要谨慎，判活也要谨慎。

**Q：DBC 里信号怎么读？车速 0x200 怎么解析？**
A：`SpeedKmh 0|16@1+ (0.1,0)`：起始位 0、16 位、@1=小端、+=无符号，缩放 0.1。
原始值 1000 → 100.0 km/h。SpeedValid 是单独 1 位标志位，速度信号不可信时
（传感器故障）联锁/EBM 一律按"最危险"处理——比如门联锁在 speed_valid=False 时
禁止开门，EBM 缓解条件要求 speed_valid 为真。

### 诚实边界（主动交代，反而加分）
**Q：这是真实列车协议吗？**
A：不是。报文协议为模拟设计，红线是**不还原真实车型协议（涉密）**。但安全逻辑
（联锁/EBM/EBR/错误状态机）对标真实列控系统设计。诚实声明是项目原则——README、
safety_case、tutorial 三处都明确写了。

**Q：SIL 认证是真的吗？**

完整配置管理——那超出开源项目范围，我明确标注"非真实认证"。

**Q：接真实硬件了吗？**
