## 1. 立项（为什么做 / 边界 / 成功标准）

### 1.1 背景与动机（面试叙事根基）
- 我在 tcms-can-test 上**手写了 960 个 pytest 用例，语句覆盖率 97.96%**（2026-09 实测）。
- 行业问题：LLM 写测试是热点，但**"怎么证明 LLM 写的用例是好的"** 普遍没答案。
- 本项目回答它：把质量评估做成可复现流水线（解析率 / 执行通过率 / judge 分）。

### 1.2 范围边界（严格遵守，防蔓延）
- **做**：从 TCMS 真实资产（DBC/场景/需求）→ LLM 生成用例 → 真实执行 → 量化质量。
- **不做**（一期外）：不做训练/微调；不做通用代码生成平台；不做 UI/服务化；
  不做与 TCMS 无关的泛化生成——所有实验必须挂在 TCMS 域内，保证叙事聚焦。

### 1.3 成功标准（可验收，非口号）
1. 二期结束时，能在 **tcms-can-test 上真实跑通**「需求 → 生成 → 执行 → 报告」全链路，
   且报告中数字（用例数/通过率/覆盖率）**全部实测可复现**。
2. 至少一份**多模型对比实验报告**（docs/experiments/），有明确结论
   （哪个模型 + 什么 prompt 策略质量最好，附数据表）。
3. 仓库工程水准不降：测试全绿、覆盖率门禁 ≥90%、ruff 全过、CI 绿。
4. 面试可讲 3 分钟故事：动机 → 架构 → 实验 → 结论 → 下一步。

## 3. 研究纪律（怎么研究才算合格）

1. **假设驱动**：每个实验先写「假设 → 实验设计 → 指标 → 判定标准」，再动手。
   例：*假设 DeepSeek + few-shot 示例的 parse_rate 显著高于零样本*。
2. **控制变量**：单次实验只改一个变量（模型 / prompt / 输入），其余固定并记录。
3. **可复现**：所有实验有固定 seed/温度/版本记录；跑实验的命令写进 docs/，别人能复跑。
4. **诚实记录**：失败实验同样存档（docs/experiments/ 含 negative results），
   结论只基于数据，禁止"我觉得"。
5. **基线对照**：永远有对照（如：规则模板生成的基线 vs LLM 生成），
   否则"质量好"无意义。

## 4. 测试纪律（本项目双重身份：做测试 且 被测）

### 4.1 作为"AI 测试工具"，必须自己先有最好的测试（面试核心叙事）
- **门禁**：pytest 全绿 + 覆盖率 ≥90%（`--cov-fail-under=90`）+ ruff 全过 + CI（3.10-3.12）。
- 每个新模块必须有单测（loader/executor/judge/llm 的确定性分支全测）；
- LLM 非确定性部分用 **mock/录播** 测（不依赖网络，CI 可跑）。

### 4.2 作为"测 AI 生成质量"，质量口径必须可信
- `parse_rate`（能结构化解析的比例，含残缺样本诚实统计）
- `exec_pass_rate`（真实执行通过率，一期 mock、二期真实 pytest）
- `quality_score`（judge 0-100，规则 rubric；后续与真 LLM judge 交叉验证）
- **口径文档**（docs/metrics.md）：每个指标的定义/分母/边界情况写清楚，面试扛追问。

## 5. 工程原则（铁律）

| # | 原则 | 含义 |
|---|---|---|
| 1 | **数字实测，禁止编造** | 一切结论可复现；写进报告的每个数有对应命令/文件 |
| 2 | **先测后报** | 每个里程碑：测试全绿 + 自测脚本 PASS 才允许汇报 |
| 3 | **小步提交** | 原子 commit（英文），一次一个逻辑变更；CI 保持绿 |
| 4 | **不破坏门禁** | 覆盖率 90% 只升不降；新代码必带测试 |
| 5 | **离线优先** | 核心链路不依赖外部 API（mock 可跑）；真实 LLM 是可选增强 |
| 6 | **文档同步** | 代码变更 → README/口径文档同步更新，不留债 |
| 7 | **聚焦不蔓延** | 超出范围的需求记入 backlog（docs/backlog.md），不在本期做 |
| 8 | **诚实边界** | LLM 生成质量不达标就如实报告并分析，不硬凑结论 |
