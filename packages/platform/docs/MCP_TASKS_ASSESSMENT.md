# Tasks 扩展对照自评（Slice 4）

> 建立：2026-09-21 ｜ 定位：**对照自评**，不是实现 —— 结论是"暂不实现，但已具备语义等价物"
> 规范依据：MCP 2026-07-28 的 **Tasks 扩展**（<https://modelcontextprotocol.io/extensions/tasks/overview>）：
> 长任务的异步执行 + 轮询 + 中途输入 + 持久句柄（opt-in，双方在初始化时协商）

---

## 1. 一句话结论

**协议层未实现 Tasks 扩展；但"长任务可暂停/可恢复/可人工干预"的语义在本项目里已经存在**，
只是长在**平台自己的检查点与审批节点**上，而不是长在 MCP 协议层。

所以诚实的说法不是"我们没有长任务能力"，而是：
**"这套语义我实现过（LangGraph 检查点 + interrupt 审批 + 断点续跑），只是没把它包装成 MCP 的 Tasks 扩展协议。"**

---

## 2. 逐条对照

| Tasks 扩展要求 | 本项目已有 | 差距（诚实） |
|---|---|---|
| **异步执行**：请求立即返回句柄，后台继续跑 | ✅ 平台内有后台任务与运行轨迹（`runner.py` 检查点 / 回放） | ⛔ MCP 面仍是**同步**：`run_scenario` 阻塞到执行结束才回包 |
| **轮询**：客户端按 handle 查询进度/结果 | 🟡 平台有运行记录与白盒事件流（SSE）；MCP 面只有 `notifications/progress`（推送型，非轮询型） | ⛔ 无 `tasks/get` 式查询接口 |
| **持久句柄**：句柄跨进程/重启有效 | ✅ **SQLite 检查点** + 断点续跑（ADR 里明确写了"可暂停/续跑/逐超级步回放"） | ⛔ 句柄没有映射到 MCP 的 task id |
| **中途输入**（human-in-the-loop） | ✅ **审批节点**（ADR-007：审批放独立节点，副作用只写在 `interrupt()` 之后）；**本轮的 elicitation 已把它接到协议层** | 🟡 走的是 `elicitation/create`，不是 Tasks 的中途输入通道 |
| **双方协商**（opt-in 扩展） | ⛔ 未做：`initialize` 的 capabilities 里没有声明扩展 | ⛔ 未声明、未协商 |

**覆盖度自评**：语义等价物 **3/5**（异步执行 ✅语义/⛔协议、持久句柄 ✅、中途输入 ✅）；
协议层实现 **0/5**。

---

## 3. 为什么现在不做（三条理由，都不是"懒"）

1. **执行体是秒级的、原子的**：`run_yaml` 单场景执行在秒级完成，且引擎调用不可中断。
   为一个秒级操作引入"异步句柄 + 轮询 + 持久化任务表"，是把复杂度买在了不需要它的地方。
2. **单机自托管定位**：当前 HTTP 面是单进程 + Bearer token；Tasks 扩展的价值主要在
   **多客户端 / 长时任务 / 断线重连** 的场景，与"本机演示与自证"的定位不匹配。
3. **已有的检查点才是真的持久句柄**：它的语义比 Tasks 扩展更丰富（逐超级步回放、失败恢复），
   现在把它降级包装成 task id 反而是**信息损失**。

> 一句话：**先有真实的长任务需求，再上 Tasks 扩展**；否则就是为规范清单打勾。

---

## 4. 如果将来要做：最小路线（3 步）

1. `initialize` 里声明扩展能力（`capabilities.extensions.tasks`），并**只在客户端也声明时**启用。
2. 新增 `tasks/create`（立即返回 task id）+ `tasks/get`（进度/结果）+ `tasks/cancel`；
   **task id 直接复用 SQLite 检查点的 run id**（不另建状态机）。
3. `run_scenario` 增加 `async=true`：返回 task id，后台线程执行，进度复用现有
   `notifications/progress` 与白盒事件流。

**验收标准**：任务在**服务重启后**仍可按 id 查到结果（这条才是 Tasks 扩展的真正门槛）。

---

## 5. 面试讲法（3 句话）

1. "MCP 的 Tasks 扩展我**没实现协议层**，但它的五个语义里我实现了三个——检查点当持久句柄、
   审批节点当中途输入、白盒事件流当进度。"
2. "我**主动没做**这个扩展：我的执行体是秒级且原子的，上异步是把复杂度买在不需要它的地方。"
3. "如果要做的门槛我已经想清楚了：**重启后仍能按 id 查到结果**——这才是 Tasks 的真正门槛，
   而不是加一个 `tasks/create` 方法名。"

> 这种"知道规范、评估过、给出不做的理由与再做的门槛"的回答，比"我实现了 Tasks 扩展"更难被追问倒。
