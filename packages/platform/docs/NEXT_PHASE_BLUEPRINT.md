## 2. 资产真实化（回应"现实中只有这些吗"）

**调研结论（全带来源，见下）**：当前 8/36/22/19/18/4 属**教学演示级**，比真实 TCMS **少 1–2 个数量级**。

| 维度 | 当前 | 真实量级锚点 | 来源 |
|---|---|---|---|
| 整车信号 | 36 | **上千个**（RIOM 分布采集） | [EKE RIOM](https://www.eke-electronics.com/what-is-a-riom/) |
| 车辆级端口 | 8 报文 | **≥500 MVB 端口**监听需求；Class1 上限 4095 | [城轨无线传输装置](https://qikan.cmes.org/sbglywx/CN/PDF/10.16621/j.cnki.issn1001-0599.2022.06.53)、[Wikipedia TCN](https://en.wikipedia.org/wiki/Train_communication_network) |
| 功能域 | 4 | **13 个系统**（S1000D 分类 01-13：牵引/制动/车门/空调/HVAC/PIS/高压/辅助/电池/照明/烟火/走行部…） | [S1000D 动车组应用](http://tljsjyy.xml-journal.net/cn/article/pdf/preview/4297.pdf) |
| 故障码 | 22 | 单车型**数百~上千条**，4 位 hex（系统+等级+现象），实车到 7xxx 段 | [动车组故障编码标准](https://www.sciengine.com/doi/pdf/F4BE320262E94E999329BDF1CD3452FA)、[CRH380B 7174](https://cn.chinadaily.com.cn/a/201902/25/WS5c734873a31010568bdcba48.html) |
| 需求 | 18 | 行业按 EN 50128 组织**百条级 SRS + RTM 四向追溯**（需求→用例→故障→场景） | [Parasoft EN50128](https://www.parasoft.com/white-paper/satisfying-en-50128-requirements-with-parasoft/)、[CN106814730A](https://patents.google.com/patent/CN106814730A/zh) |
| 场景 | 19 | 预案 3 层组织（官方预案→演练科目→司机题库），常见 **8–15 类剧本族** | [国家铁路局预案](https://www.nra.gov.cn/jglz/fgzd/gfwj/zt/qt/202204/P020220406007989285103.pdf)、[交通部演练办法](https://xxgk.mot.gov.cn/xzgfxwj/202408/t20240807_4147491.html) |

**扩法建议（分级，控制成本）**：
- **P-A（数据层，先把量做对）**：报文/信号扩到"代表性几十~上百条 + 周期分级 25/50/100/250ms + 多网段(已具备)"；故障按 13 系统×每系统 10-30 条铺到数百；功能域 4→8-10（补 HVAC/受电弓高压/电池/走行部）；需求按功能域×SIL 扩容到 60-100；场景按 8-15 类剧本族组织（每类多变异）。
- **P-B（语义层）**：资产全部挂系统域标签（13 系统分类法）+ 周期/等级/前置条件等结构化属性——这直接服务你的"原子化组合"（组合器按域/等级/时序约束拼装）。
- 红线仍守：数字机器自证、锚定真实标准（不编造车型精确数据，用"真实结构+示意实例"并标注 derived）。

## 4. 分层有界知识库（回应"向量+RAG 太浅/会迷失/要有边界"）

认同：一句"由向量和 RAG 构成"确实浅。设计升级为**分层记忆 + 有界分片 + 连贯检索**：

```
L0 资产原子层   信号/报文/故障/需求/场景/功能/设备（结构化 schema，source of truth）
L1 领域知识层   13 系统分类树 + 标准锚点(EN50128/GB/T28029/UIC556) + 危害/联锁/阈值（图谱）
L2 运行记忆层   run/复盘/采纳驳回（GraphSink 沉淀，按时间分片，可归档）
L3 对话/会话层  用户偏好/历史（不污染 L0-L1）

索引边界策略：
- 分片索引：按 13 系统域分片（向量库=多分区而非一个无限大池），检索先路由到域再语义
- 图谱路由：先图谱定位域/实体 → 域内语义 topk（"不会在庞大库中迷失"的实现）
- 库有上限：每分区容量上限 + 淘汰/归档策略（L2 按时间滚动、L0/L1 只由资产变更驱动重建）
- 连贯检索：会话上下文携带（同域追问不走全局重查）+ 邻接连续扩跳
```

这与 fresume 的"行业信息库+图谱对齐"同构——我们做列车域版。

## 5. fresume 对标借鉴（回应 7）

fresume 是 AI 简历分析+JD 匹配驾驶舱（[官网](https://fresume.odsy.com.cn)，学生作品、TRAE 大赛）。调研拆出**最有价值的是它的 AI 约束与溯源设计**（详见子调研）。可落地到我们：

| fresume 设计 | 我们借鉴 | 价值 |
|---|---|---|
| **三栏溯源**：原文→已确认 KB 事实→AI 改写建议，明示"引用 KB 更可信" | RAG 证据链升级为"源资产→图谱事实→Agent 建议"三栏可视化，未引用图谱的生成明确标注 | 让"AI 不是乱说"看得见 |
| **改写模式枚举卡**（量化/关键词对齐/精简…非自由发挥） | Agent 编排意图枚举（补边界/补级联/对齐需求/压时序），LLM 只做枚举内选择+文案 | 防 LLM 乱写测试 |
| **主库=AI 只读 source of truth** | 资产/需求基线不可由 AI 回填篡改（人工采纳才写回） | 数据可信 |
| **固定四维雷达评分** | Agent 匹配质量拆四维雷达：覆盖/相关性/可执行/断言强度 | 评审更直观 |
| 版本不落地、采纳才应用、诚实长任务提示、双输入通道、运营信息库+人工审核 | 采纳驳回流/长任务文案/截图+粘贴双入口/自定义资产审核流 | 产品丝滑度 |

结论：它的"名"来自**产品化包装与约束式 AI 交互**，不在底层算法——我们资产与引擎更深，缺的是同样的产品化表达。本地完善完全可行（不租服务器，本地 Web 已够演示）。
