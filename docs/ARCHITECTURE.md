# 架构说明（Architecture）

> 本文描述 **现状**（已落地的代码），不是愿景。每条陈述都能在代码里指到。
> 未落地的部分统一标注 ⬜ 并注明计划里程碑。

---

## 1. 分层与依赖方向

```
packages/agent      认知层：循环 / 工具面 / 记忆 / 评测        ⬅ 本项目主战场
      ↓ 只依赖库（不依赖 Web 层）
packages/platform   知识底座：资产模型 + 图谱 + 混合检索 + FastAPI + Web UI
      ↓
packages/engine     领域引擎：CAN 仿真 / DBC 编解码 / 场景执行 / 安全逻辑 / 真实资产
packages/testgen    生成与自证（依赖 engine，与 platform 并列）
```

**单向依赖**，同层不互相 import。agent 只以**库**方式使用 platform：
这意味着 agent 可以脱离 FastAPI 单独跑（CLI / 评测 / CI），也让 UI 与 Agent
可以各自演进。

### 为什么 agent 不直接用 platform 的 Web API
Web 层是给人用的契约（HTTP/JSON、面向页面），Agent 需要的是**低延迟、可审计、
可批量调用的函数级工具面**。走 HTTP 会把"工具调用"变成"网络请求"，既慢又难做
权限门禁与审计。因此 agent 直接 import platform 的库函数，再用自己的注册表包一层。

## 2. Agent 运行时（packages/agent）

### 2.1 图拓扑（LangGraph StateGraph）

```
START → plan → agent ─┬─(有工具调用 且 预算未超)→ act ─┬─(有待审批项)→ approve → agent
                      │                              └─(无)──────────────────→ agent
                      └─(收尾 / 预算耗尽)────────────→ verify → report → END
```

| 节点 | 职责 | 关键设计 |
|---|---|---|
| `plan` | 目标 → 计划清单 + 锚定目标故障 | 用 platform 的**规则**解析器（`freeform.parse_free_goal`），不猜故障键 |
| `agent` | LLM 决策：调哪个工具 / 收尾 | **唯一的自由决策节点**；system prompt 里的工具清单由注册表生成，不手写 |
| `act` | 执行**不需要审批**的工具调用 | 权限门禁 + 审计 + 观察回填；需审批的写入 `pending`，**本节点绝不 interrupt** |
| `approve` | **human-in-the-loop 审批（唯一中断点）** | `interrupt()` 暂停 → 人决策 → 恢复后执行获批项 / 如实拒绝其余 |
| `verify` | **引用强制校验** | 结论引用的每个资产 id 回真实图谱核对；幻觉引用在此被机器抓住 |
| `report` | 汇总终局判定 | 产出结构化 verdict（供评测体系直接消费），并**披露被拒的写入** |

**为什么 verify 是独立节点而不是塞进 report**：校验必须是一等公民。它产出的
结构化 verdict 既供人读，也供评测消费（M6 指标直接取它）。藏在报告生成里就没法
对"校验本身"做回归测试。

### 2.2 状态与 reducer

`AgentState`（`state.py`）用 LangGraph 的 reducer 语义：

| 字段 | reducer | 含义 |
|---|---|---|
| `messages` | `add_messages` | 对话/工具消息自动追加，ReAct 的载体 |
| `trace` | `operator.add` | **审计事件流累加**，轨迹是一等产物 |
| `evidence` / `sources` | `operator.add` | 证据与引用累加 |
| `steps` | 无（覆盖） | **显式预算计数器**，不依赖框架内部计数 |

设计要点：预算必须是**可审计的显式状态**，而不是藏在运行时里的黑盒。

### 2.3 工具面与四级权限

`permissions.py` 定义副作用分级，`tools/registry.py` 强制执行：

| 级别 | 含义 | 管控 | 现状 |
|---|---|---|---|
| **R0 只读** | 知识底座查询 / 资产枚举 / 图谱 / DSL 参考 | 自由调用 | ✅ 9 个工具 |
| **R1 沙箱写** | 生成受约束用例草稿（可丢弃） | 只写沙箱，编译期校验 | ✅ 1 个工具 |
| **R2 真实执行** | 跑场景 / 跑自造用例 | **子进程 + 真超时 + 产物归档** | ✅ 3 个工具 |
| **R3 持久化** | 写记忆、提升归档 | **人工审批 + 引用门禁** | ✅ 2 个工具 |

### 2.3.2 R1 沙箱写：为什么"受约束"是关键

LLM 写的用例走 testgen 的 **ExecutionIntent DSL**，约束由**编译器**执行，
不由提示词祈求：

- 字段缺失 / 类型错 / **未知 op** → Pydantic 白名单当场拒绝
  （`未知原语 'expect_teleport'（白名单见 SETUP_OPS/ASSERT_OPS）`）；
- 未知 kind / 不可编译 → `compile_case` 拒绝，工具如实报错并给出可用词表。

于是"LLM 写测试"有了机器闸门：**写得出 ≠ 跑得起来**，跑不起来就当场诚实失败。

> **词表只有一个真源**：`dsl_reference` 直接 `import` testgen 的 `SETUP_OPS/ASSERT_OPS/EXEC_KINDS`，
> **绝不手抄**。最初我手抄了一份，防漂移测试立刻抓到它与编译器不一致（漏了
> `inject_fault`/`recover_fault`）。手抄的"说明书"会误导模型写出永远编译不过的用例。

### 2.3.3 反思自愈为什么交给 Agent，而不是内置循环

原 testgen 有一个写死的 `reflect_loop`（失败→分类→带证据重写→重跑）。
这里**不内置**该循环：`run_draft` 只返回真实失败输出与 `failure_lines` 要点，
由 Agent 自己决定要不要重写、怎么重写（同一 `draft_id` 覆盖即可完成修复迭代）。

这正是「Agent」与「固定流水线」的分野：流水线只能按预设分支走，
Agent 可以自己判断、改变策略、甚至放弃。

**双保险**（不是提示词礼貌）：
- 超过级别的工具**不出现在**送给模型的 schema 里；
- 即便模型绕过 schema 直接点名，`invoke()` 也会拒绝执行并记审计。

> 注册表**注册全量工具面**，由 `max_level` 门禁。若按档位选择性注册，第 2 道防线
> 永远不会被触发、沦为死代码——这是测试抓出来的设计问题（见 `test_execution_tools.py`）。

**为什么不用 LangGraph 的 `ToolNode` 直接跑**：`ToolNode` 不认识"权限级别"。
在安全关键域，每次调用都必须先过门禁、再留审计，所以执行路径必须自己收口。

### 2.3.1 human-in-the-loop 审批的实现要点

`approve` 节点是**全图唯一调用 `interrupt()` 的地方**，这是刻意的：

> LangGraph 在 resume 时会让**被中断的节点从头重跑**。因此 `interrupt()` 之前
> 的代码会执行两次——那里只能放无副作用的准备动作（读 state、构造审批载荷）；
> 真正的执行必须写在 `interrupt()` **之后**，它只会跑一次。
> 这条约束不是猜的：用最小实验实测过（`prep` 执行 2 次、`after-resume` 执行 1 次）。

据此把执行拆成两个节点：
- `act`：执行不需要审批的工具（有副作用，但**不 interrupt**，因此不会重跑）；
- `approve`：只处理待审批项，interrupt 前零副作用，interrupt 后执行/拒绝。

**安全默认**：`approver=None` 时**一律拒绝**——没有人在场就不写。
拒绝也是**一等结果**：理由会作为工具结果回填给 Agent（它不是静默失败），
并写进轨迹与报告（"被拒：write_memory —— 该写入未发生"）。

### 2.3.1 真执行为什么要独立子进程

`run_scenario` / `verify_fault_action` 在**独立子进程**里跑上游引擎
（`_exec_worker.py`），而不是同进程调用：

- 只有独立进程才能被**真正杀死**。线程超时只能"放弃等待"，底层仿真还在跑——
  那是假超时，会让"没超时"的结论也不可信；
- 进程崩溃 / 解释器状态污染不会带倒 Agent 主进程；
- 每次执行产物落盘到 `沙箱/<run_id>/`，结论可事后复核。

### 2.4 离线规则臂（`models.py`）

无 API key 时不是"给个假回复"，而是换上一个**确定性规则参考实现**：
它走**同一张图、同一套工具、同一套权限与审计**，只是决策由规则（而非 LLM）做出。

带来三个好处：
1. 离线运行也真实覆盖 harness 的全部基础设施（测试可信的前提）；
2. 产出轨迹作为 LLM 的**对照基线**（M6 的 A/B 就是"规则臂 vs LLM 臂"）；
3. 结果 100% 可复现，适合作回归门禁。

`model_kind ∈ {"llm", "offline-rule"}` 如实标注，**绝不把规则结果说成 AI 决策**。

### 2.5 轨迹持久化与回放

每次运行绑定 `thread_id`，`SqliteSaver` 在**每个超级步后**落盘完整状态：
- 可回放（`AgentRunner.history(thread_id)` 逐超级步查看）
- 可续跑（崩溃后从最后快照继续）
- 可审计（状态即证据）

## 2.6 四层记忆：写进去必须**读得出来**，否则只是装饰

| 层 | 实现 | 内容 | 写入纪律 |
|---|---|---|---|
| **工作记忆** | LangGraph `AgentState` | 当前 trajectory（+ 单条工具结果截断） | 自动 |
| **情景记忆** | `memory/journal.py` | 运行日志 JSONL（目标/结果/工具/失败/引用） | 自动（机器事实，无判断） |
| **语义记忆** | platform 知识底座 | 资产 / 图谱 / 混合检索 | 来自真实资产 |
| **程序性记忆** | `memory/consolidate.py` | 从历史挖出的可复用经验（技能） | **两道门禁** |

### 召回 → 注入 → 影响

```
START → recall → plan → agent ─┬─→ act ─┬─→ approve → agent
                               │        └──────────→ agent
                               └─(收尾)─→ verify → report → END
```

`recall` 节点按当前目标召回情景 + 程序性记忆，渲染成文本块，
由 `agent` 节点注入系统提示词（`_system_message(..., memory_context)`）。
轨迹里会记录"这次想起了什么、相似度多少"——**记忆的使用是可审计的**。

> 首次运行：「无相关历史记忆（首次遇到这类目标）」——明确区分"没想起来"与"没做召回"。

### 记忆让运行"路径依赖"——这是特性不是缺陷

开启记忆后，第二次运行的轨迹**应当**与第一次不同。因此可复现性的准确表述是
「同一配置 + 同一记忆状态下可复现」，测试也据此拆成两条
（`test_run_is_deterministic_without_memory` / `test_memory_makes_runs_path_dependent`）。
`memory_enabled=False` 是为 R7 的「有记忆 vs 无记忆」A/B 预留的开关。

### 离线巩固与两道门禁

巩固**不在运行时做**：在线写记忆会被单次结果牵着走，一次侥幸通过就可能沉淀成"经验"。
离线巩固看的是**跨运行的重复模式**（≥N 次才成提案），这正是 sleep-time compute 的直觉。

写入前必须过两道**互相不可替代**的门禁：

1. **引用门禁**：引用的资产 id 必须真实存在（复用 `verify` 的同一套校验）；
2. **证据门禁**：必须指出它来自哪些运行，且这些 `run_id` **真的在日志里**。

第 2 条是这里特有的：**一条"经验"若拿不出出处的运行记录，就不配进长期记忆**。
它防的是"编一条听起来很对的规律"——那种东西一旦入库，会被后续召回反复强化，
比单次回答出错严重得多。`consolidate --write` 之前默认只出提案（先看清再写）。

### 召回通道的诚实口径

用 platform 的字符级哈希通道（与知识底座同一口径），衡量的是**字符重合度，不是语义**：

- 「验证车门故障必须触发降级处置」 vs 「验证车门故障不能发车」→ 高重合 ✓
- 「车厢门打不开」 vs 「车门故障」→ 重合有限（需要真语义通道，属 R6 范围）

**不把字符重合度说成语义检索**——这条纪律在原三仓里就是明文规定。

## 2.7 RAG 升级：把"三通道"从宣称变成事实

### (1) 图谱真正进入融合——但只能作为**补充通道**

审计发现：README 曾声称"BM25 + 向量 + 图谱三通道 RRF 融合"，而代码里
`rrf([vec_ids, lex_ids])` 只有两路。本轮把它变成真的，过程中有个**关键实测**：

| 方案 | 结果 |
|---|---|
| 图谱与文本两路**等权竞争** | golden 从 14/14 掉到 **12/14**（图谱候选 100% 已被文本覆盖，只搅乱排序） |
| 图谱作为**纯补充**（剔除文本已召回项） | golden **14/14**，且症状式查询多召回 3 条 |

结论：**一个只稀释不增益的通道没有存在理由**，所以图谱被限定为"只交出文本两路没找到
的文档"——只可能增加召回，不可能稀释。`rrf()` 相应增加了 `weights` 参数（默认仍等权）。

**图谱的真实价值点（实测，非设计预期）**：

| 查询类型 | 仅图谱召回 |
|---|---|
| `车门故障 不能发车` / `SR-21` / `超速 降级`（有实体名） | 0 |
| **`仪表盘闪烁`（症状式，无实体名）** | **3**（`system:SYS-BRAKE`、`function:F-ATP`、`fault:light_group_fault`） |

每条命中带 `channels` 标注，"三通道"可**逐条核对**而不是一句宣称。

### (2) 特征重排（而非 LLM 重排）

融合只用**排名**，丢掉了"这条为什么被召回"。重排用四个可解释特征捡回来：
通道共识 / 查询字符覆盖 / doc_id 字面命中 / 类型先验。权重显式写在 `rerank.py::FEATURES`。

**不用 LLM 重排**：① 不可离线复现，检索质量就进不了回归门禁；② 本项目已有"LLM 只能在
候选内重排、不得引入新文档"的纪律，在检索最底层引入 LLM 只会把不确定性带进来；
③ 特征权重可以被**评测数据标定**，比拍脑袋调 prompt 靠谱。

**实测（14 条检索 golden）**：

| 指标 | 基线 | 重排后 |
|---|---|---|
| `min_at` 达标 | 14/14 | **14/14**（持平） |
| 期望项进 **top-1** | 12/14 | **14/14**（+2） |
| 被排差的查询 | — | **0** |

这三行被写成断言（`test_rerank.py`），今后改权重把它改差了测试会响。

### (3) 引用强制校验的强化：补上一个**半条链路**的漏洞

此前 `verify` 只校验"工具返回过的 id"（`state.sources`）。这意味着：

> 模型只要在**结论正文**里写一个从未被任何工具返回过的 `fault:xxx`，
> 那条引用根本不进校验链——**幻觉只要不经过工具就查不出来**。

校验器看起来很严，实际只覆盖了半条链路。现在正文里的 `kind:key` 也被正则抽出、
与工具链引用一起核对，且 verdict 区分来源（`from: tool` / `from: answer_text`），
失败原因也分开表述——便于定位幻觉产生在哪一环。

## 5. 实测对照：两个臂的真实差异

同一目标「验证超速必须触发降级处置」：

| | 离线规则臂 | LLM 臂 |
|---|---|---|
| 步数 / 工具调用 | 5 步 / 4 次（检索→查字典→真执行→列场景） | **2 步 / 1 次**（直接真执行验证） |
| 策略 | 方法论式：先把语义查清再验证 | **目标导向**：问题就是"引擎怎么说"，那就直接问引擎 |
| 结论形态 | 字典语义 + 引擎验证并列 | 以**引擎断言表**为主证据，并引用归档路径 |

这不是"LLM 更聪明"的空话，而是可复现的行为差异：**规则臂把流程走全，
LLM 臂走捷径**。两者都有价值——规则臂适合回归门禁（确定性强），LLM 臂适合
真实任务（效率高、会挑重点）。R6 的 A/B 评测就建立在这个对照上。
