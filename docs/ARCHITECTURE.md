# 架构说明（Architecture）

> 本文描述 **现状**（已落地的代码），不是愿景。每条陈述都能在代码里指到。
> 未落地的部分统一标注 ⬜ 并注明计划里程碑。

---

## 1. 分层与依赖方向

```
packages/agent      认知层：循环 / 工具面 / 记忆 / 评测        ⬅ 本项目主战场
      ↓ 只依赖库（不依赖 Web 层）
packages/platform   知识底座：资产模型 + 图谱 + 混合检索 + FastAPI + Web UI
      ↓
packages/engine     领域引擎：CAN 仿真 / DBC 编解码 / 场景执行 / 安全逻辑 / 真实资产
packages/testgen    生成与自证（依赖 engine，与 platform 并列）
```

**单向依赖**，同层不互相 import。agent 只以**库**方式使用 platform：
这意味着 agent 可以脱离 FastAPI 单独跑（CLI / 评测 / CI），也让 UI 与 Agent
可以各自演进。

### 为什么 agent 不直接用 platform 的 Web API
Web 层是给人用的契约（HTTP/JSON、面向页面），Agent 需要的是**低延迟、可审计、
可批量调用的函数级工具面**。走 HTTP 会把"工具调用"变成"网络请求"，既慢又难做
权限门禁与审计。因此 agent 直接 import platform 的库函数，再用自己的注册表包一层。

## 2. Agent 运行时（packages/agent）

### 2.1 图拓扑（LangGraph StateGraph）

```
START → plan → agent ─┬─(有工具调用 且 预算未超)→ act ─┬─(有待审批项)→ approve → agent
                      │                              └─(无)──────────────────→ agent
                      └─(收尾 / 预算耗尽)────────────→ verify → report → END
```

| 节点 | 职责 | 关键设计 |
|---|---|---|
| `plan` | 目标 → 计划清单 + 锚定目标故障 | 用 platform 的**规则**解析器（`freeform.parse_free_goal`），不猜故障键 |
| `agent` | LLM 决策：调哪个工具 / 收尾 | **唯一的自由决策节点**；system prompt 里的工具清单由注册表生成，不手写 |
| `act` | 执行**不需要审批**的工具调用 | 权限门禁 + 审计 + 观察回填；需审批的写入 `pending`，**本节点绝不 interrupt** |
| `approve` | **human-in-the-loop 审批（唯一中断点）** | `interrupt()` 暂停 → 人决策 → 恢复后执行获批项 / 如实拒绝其余 |
| `verify` | **引用强制校验** | 结论引用的每个资产 id 回真实图谱核对；幻觉引用在此被机器抓住 |
| `report` | 汇总终局判定 | 产出结构化 verdict（供评测体系直接消费），并**披露被拒的写入** |

**为什么 verify 是独立节点而不是塞进 report**：校验必须是一等公民。它产出的
结构化 verdict 既供人读，也供评测消费（M6 指标直接取它）。藏在报告生成里就没法
对"校验本身"做回归测试。

### 2.2 状态与 reducer

`AgentState`（`state.py`）用 LangGraph 的 reducer 语义：

| 字段 | reducer | 含义 |
|---|---|---|
| `messages` | `add_messages` | 对话/工具消息自动追加，ReAct 的载体 |
| `trace` | `operator.add` | **审计事件流累加**，轨迹是一等产物 |
| `evidence` / `sources` | `operator.add` | 证据与引用累加 |
| `steps` | 无（覆盖） | **显式预算计数器**，不依赖框架内部计数 |

设计要点：预算必须是**可审计的显式状态**，而不是藏在运行时里的黑盒。

### 2.3 工具面与四级权限

`permissions.py` 定义副作用分级，`tools/registry.py` 强制执行：

| 级别 | 含义 | 管控 | 现状 |
|---|---|---|---|
| **R0 只读** | 知识底座查询 / 资产枚举 / 图谱 / DSL 参考 | 自由调用 | ✅ 9 个工具 |
| **R1 沙箱写** | 生成受约束用例草稿（可丢弃） | 只写沙箱，编译期校验 | ✅ 1 个工具 |
| **R2 真实执行** | 跑场景 / 跑自造用例 | **子进程 + 真超时 + 产物归档** | ✅ 3 个工具 |
| **R3 持久化** | 写记忆、提升归档 | **人工审批 + 引用门禁** | ✅ 2 个工具 |

### 2.3.2 R1 沙箱写：为什么"受约束"是关键

LLM 写的用例走 testgen 的 **ExecutionIntent DSL**，约束由**编译器**执行，
不由提示词祈求：

- 字段缺失 / 类型错 / **未知 op** → Pydantic 白名单当场拒绝
  （`未知原语 'expect_teleport'（白名单见 SETUP_OPS/ASSERT_OPS）`）；
- 未知 kind / 不可编译 → `compile_case` 拒绝，工具如实报错并给出可用词表。

于是"LLM 写测试"有了机器闸门：**写得出 ≠ 跑得起来**，跑不起来就当场诚实失败。

> **词表只有一个真源**：`dsl_reference` 直接 `import` testgen 的 `SETUP_OPS/ASSERT_OPS/EXEC_KINDS`，
> **绝不手抄**。最初我手抄了一份，防漂移测试立刻抓到它与编译器不一致（漏了
> `inject_fault`/`recover_fault`）。手抄的"说明书"会误导模型写出永远编译不过的用例。

### 2.3.3 反思自愈为什么交给 Agent，而不是内置循环

原 testgen 有一个写死的 `reflect_loop`（失败→分类→带证据重写→重跑）。
这里**不内置**该循环：`run_draft` 只返回真实失败输出与 `failure_lines` 要点，
由 Agent 自己决定要不要重写、怎么重写（同一 `draft_id` 覆盖即可完成修复迭代）。

这正是「Agent」与「固定流水线」的分野：流水线只能按预设分支走，
Agent 可以自己判断、改变策略、甚至放弃。

**双保险**（不是提示词礼貌）：
- 超过级别的工具**不出现在**送给模型的 schema 里；
- 即便模型绕过 schema 直接点名，`invoke()` 也会拒绝执行并记审计。

> 注册表**注册全量工具面**，由 `max_level` 门禁。若按档位选择性注册，第 2 道防线
> 永远不会被触发、沦为死代码——这是测试抓出来的设计问题（见 `test_execution_tools.py`）。

**为什么不用 LangGraph 的 `ToolNode` 直接跑**：`ToolNode` 不认识"权限级别"。
在安全关键域，每次调用都必须先过门禁、再留审计，所以执行路径必须自己收口。

### 2.3.1 human-in-the-loop 审批的实现要点

`approve` 节点是**全图唯一调用 `interrupt()` 的地方**，这是刻意的：

> LangGraph 在 resume 时会让**被中断的节点从头重跑**。因此 `interrupt()` 之前
> 的代码会执行两次——那里只能放无副作用的准备动作（读 state、构造审批载荷）；
> 真正的执行必须写在 `interrupt()` **之后**，它只会跑一次。
> 这条约束不是猜的：用最小实验实测过（`prep` 执行 2 次、`after-resume` 执行 1 次）。

据此把执行拆成两个节点：
- `act`：执行不需要审批的工具（有副作用，但**不 interrupt**，因此不会重跑）；
- `approve`：只处理待审批项，interrupt 前零副作用，interrupt 后执行/拒绝。

**安全默认**：`approver=None` 时**一律拒绝**——没有人在场就不写。
拒绝也是**一等结果**：理由会作为工具结果回填给 Agent（它不是静默失败），
并写进轨迹与报告（"被拒：write_memory —— 该写入未发生"）。

### 2.3.1 真执行为什么要独立子进程

`run_scenario` / `verify_fault_action` 在**独立子进程**里跑上游引擎
（`_exec_worker.py`），而不是同进程调用：

- 只有独立进程才能被**真正杀死**。线程超时只能"放弃等待"，底层仿真还在跑——
  那是假超时，会让"没超时"的结论也不可信；
- 进程崩溃 / 解释器状态污染不会带倒 Agent 主进程；
- 每次执行产物落盘到 `沙箱/<run_id>/`，结论可事后复核。

### 2.4 离线规则臂（`models.py`）

无 API key 时不是"给个假回复"，而是换上一个**确定性规则参考实现**：
它走**同一张图、同一套工具、同一套权限与审计**，只是决策由规则（而非 LLM）做出。

带来三个好处：
1. 离线运行也真实覆盖 harness 的全部基础设施（测试可信的前提）；
2. 产出轨迹作为 LLM 的**对照基线**（M6 的 A/B 就是"规则臂 vs LLM 臂"）；
3. 结果 100% 可复现，适合作回归门禁。

`model_kind ∈ {"llm", "offline-rule"}` 如实标注，**绝不把规则结果说成 AI 决策**。

### 2.5 轨迹持久化与回放

每次运行绑定 `thread_id`，`SqliteSaver` 在**每个超级步后**落盘完整状态：
- 可回放（`AgentRunner.history(thread_id)` 逐超级步查看）
- 可续跑（崩溃后从最后快照继续）
- 可审计（状态即证据）

## 2.6 四层记忆：写进去必须**读得出来**，否则只是装饰

| 层 | 实现 | 内容 | 写入纪律 |
|---|---|---|---|
| **工作记忆** | LangGraph `AgentState` | 当前 trajectory（+ 单条工具结果截断） | 自动 |
| **情景记忆** | `memory/journal.py` | 运行日志 JSONL（目标/结果/工具/失败/引用） | 自动（机器事实，无判断） |
| **语义记忆** | platform 知识底座 | 资产 / 图谱 / 混合检索 | 来自真实资产 |
| **程序性记忆** | `memory/consolidate.py` | 从历史挖出的可复用经验（技能） | **两道门禁** |

### 召回 → 注入 → 影响

```
START → recall → plan → agent ─┬─→ act ─┬─→ approve → agent
                               │        └──────────→ agent
                               └─(收尾)─→ verify → report → END
```

`recall` 节点按当前目标召回情景 + 程序性记忆，渲染成文本块，
由 `agent` 节点注入系统提示词（`_system_message(..., memory_context)`）。
轨迹里会记录"这次想起了什么、相似度多少"——**记忆的使用是可审计的**。

> 首次运行：「无相关历史记忆（首次遇到这类目标）」——明确区分"没想起来"与"没做召回"。

### 记忆让运行"路径依赖"——这是特性不是缺陷

开启记忆后，第二次运行的轨迹**应当**与第一次不同。因此可复现性的准确表述是
「同一配置 + 同一记忆状态下可复现」，测试也据此拆成两条
（`test_run_is_deterministic_without_memory` / `test_memory_makes_runs_path_dependent`）。
`memory_enabled=False` 是为 R7 的「有记忆 vs 无记忆」A/B 预留的开关。

### 离线巩固与两道门禁

巩固**不在运行时做**：在线写记忆会被单次结果牵着走，一次侥幸通过就可能沉淀成"经验"。
离线巩固看的是**跨运行的重复模式**（≥N 次才成提案），这正是 sleep-time compute 的直觉。

写入前必须过两道**互相不可替代**的门禁：

1. **引用门禁**：引用的资产 id 必须真实存在（复用 `verify` 的同一套校验）；
2. **证据门禁**：必须指出它来自哪些运行，且这些 `run_id` **真的在日志里**。

第 2 条是这里特有的：**一条"经验"若拿不出出处的运行记录，就不配进长期记忆**。
它防的是"编一条听起来很对的规律"——那种东西一旦入库，会被后续召回反复强化，
比单次回答出错严重得多。`consolidate --write` 之前默认只出提案（先看清再写）。

### 召回通道的诚实口径

用 platform 的字符级哈希通道（与知识底座同一口径），衡量的是**字符重合度，不是语义**：

- 「验证车门故障必须触发降级处置」 vs 「验证车门故障不能发车」→ 高重合 ✓
- 「车厢门打不开」 vs 「车门故障」→ 重合有限（需要真语义通道，属 R6 范围）

**不把字符重合度说成语义检索**——这条纪律在原三仓里就是明文规定。

## 2.7 RAG 升级：把"三通道"从宣称变成事实

### (1) 图谱真正进入融合——但只能作为**补充通道**

审计发现：README 曾声称"BM25 + 向量 + 图谱三通道 RRF 融合"，而代码里
`rrf([vec_ids, lex_ids])` 只有两路。本轮把它变成真的，过程中有个**关键实测**：

| 方案 | 结果 |
|---|---|
| 图谱与文本两路**等权竞争** | golden 从 14/14 掉到 **12/14**（图谱候选 100% 已被文本覆盖，只搅乱排序） |
| 图谱作为**纯补充**（剔除文本已召回项） | golden **14/14**，且症状式查询多召回 3 条 |

结论：**一个只稀释不增益的通道没有存在理由**，所以图谱被限定为"只交出文本两路没找到
的文档"——只可能增加召回，不可能稀释。`rrf()` 相应增加了 `weights` 参数（默认仍等权）。

**图谱的真实价值点（实测，非设计预期）**：

| 查询类型 | 仅图谱召回 |
|---|---|
| `车门故障 不能发车` / `SR-21` / `超速 降级`（有实体名） | 0 |
| **`仪表盘闪烁`（症状式，无实体名）** | **3**（`system:SYS-BRAKE`、`function:F-ATP`、`fault:light_group_fault`） |

每条命中带 `channels` 标注，"三通道"可**逐条核对**而不是一句宣称。

### (2) 特征重排（而非 LLM 重排）

融合只用**排名**，丢掉了"这条为什么被召回"。重排用四个可解释特征捡回来：
通道共识 / 查询字符覆盖 / doc_id 字面命中 / 类型先验。权重显式写在 `rerank.py::FEATURES`。

**不用 LLM 重排**：① 不可离线复现，检索质量就进不了回归门禁；② 本项目已有"LLM 只能在
候选内重排、不得引入新文档"的纪律，在检索最底层引入 LLM 只会把不确定性带进来；
③ 特征权重可以被**评测数据标定**，比拍脑袋调 prompt 靠谱。

**实测（28 条检索 golden；2026-09-21 由 14 条扩容后重测）**：

> 扩容补的是症状式/易混淆/系统级查询——原表 14 条全是"故障键直问"，重排在那种查询上
> 全对，**测不出劣化**。扩容后立刻暴露 3 条**中文描述性查询**被排差（融合后都排第 1，
> 重排后被挤到 3/6/2）。曾怀疑是 `id_hit` 对中文失效；2026-09-21 把它的权重转给
> `query_overlap` 后**实测指标一字未变**——那个怀疑不成立，真正主导的是
> `channel_consensus`（0.45）。重排整体仍提升 top-1（23 → 25），但这 3 条是**仍未解决**的
> 工单——已登记在 `KNOWN_RERANK_REGRESSIONS`，新增劣化仍会立刻红。

| 指标 | 基线 | 重排后 |
|---|---|---|
| `min_at` 达标 | 28/28 | **27/28**（1 条已登记劣化） |
| 期望项进 **top-1** | 23/28 | **25/28**（+2） |
| 被排差的查询 | — | **3**（已登记为待修工单） |

这三行被写成断言（`test_rerank.py`），今后改权重把它改差了测试会响。

### (3) 引用强制校验的强化：补上一个**半条链路**的漏洞

此前 `verify` 只校验"工具返回过的 id"（`state.sources`）。这意味着：

> 模型只要在**结论正文**里写一个从未被任何工具返回过的 `fault:xxx`，
> 那条引用根本不进校验链——**幻觉只要不经过工具就查不出来**。

校验器看起来很严，实际只覆盖了半条链路。现在正文里的 `kind:key` 也被正则抽出、
与工具链引用一起核对，且 verdict 区分来源（`from: tool` / `from: answer_text`），
失败原因也分开表述——便于定位幻觉产生在哪一环。

## 2.8 评测体系（Eval Harness）

回答一个此前只能"声称"的问题：**这个 Agent 到底能不能干活，以及每个设计选择有没有用。**

### 任务集（`eval/data/tasks.yaml`，11 条）

四类任务，各测一种能力：

| kind | 测什么 | 判定 |
|---|---|---|
| `verify` | 能否验证"某故障确实触发某处置" | 达成 **且** 解析出的故障键正确 |
| `author` | 能否自己写用例并真跑通过 | 自造用例 `all_passed`（不是"工具没报错"） |
| `diagnose` | 症状多跳诊断 | 命中症状 **且** 给出候选 |
| `honest_fail` | 无关/不适配输入时能否如实拒绝 | **不通过** 且 **无编造引用** |

**负例与正例同权**：`match_rate` 的分母是全部任务——一个"什么都说好"的 Agent 会被扣分。
测试里专门有一条 `test_always_say_no_agent_cannot_farm_negative_tasks` 防反向刷分。

### 指标（分子/分母一并给出）

`match_rate` / `avg_steps` / `avg_tool_calls` / `tool_failure_rate` /
`hallucination_rate`（幻觉引用 ÷ 引用校验数）/ `self_healed`（有工具失败但任务仍达成）。

### A/B 对照臂与门禁

```
tcms-agent eval run --arms rule,llm,llm-no-memory [--out a.json]
tcms-agent eval gate --candidate a.json --baseline b.json
```

门禁比关键指标是否跌破容差（成本类指标给容差——LLM 有随机性，严格相等会天天误报），
并单独列出**回退的任务**。`test_baseline_task_set_gate` 把规则臂基线（≥10/11 且零幻觉）
固化为 CI 门禁。

### 首轮评测的实测结果（诚实版）

| 臂 | 达成 | 平均步数 | 平均工具调用 | 幻觉率 |
|---|---|---|---|---|
| `rule` | 10/11 | 4.82 | 3.82 | 0% |
| `rule-no-rerank` | 10/11 | 4.82 | 3.82 | 0% |
| **`llm`** | 10/11 | **3.45** | 3.45 | 0% |
| `llm-no-memory` | 10/11 | 3.73 | 4.18 | 0% |

**读得出的结论**：
- LLM 臂**更省步数**（3.45 vs 4.82）——它更常直接调 `verify_fault_action` 拿引擎证据，
  跳过中间检索；
- 唯一失败项在所有臂上都一样：`T-VERIFY-CRC-LOOSE`（口语省略措辞），
  即**规则解析器依赖与资产命名的重合度**——这是真实短板，不是任务写错；
- **幻觉率为 0**：引用强制校验（工具链 + 结论正文）在所有臂上都守住了。

**读不出的结论（负结果，必须如实说）**：
- **记忆与重排在这套任务集上测不出差异**。原因不是"它们没用"，而是**仪器不对**：
  - 重排影响的是**检索排序**，而任务是通过 `verify_fault_action`（真执行）达成的，
    排序变化不改变结论。重排的正确仪器是检索 golden——那里实测 **top-1 由 12/14 → 14/14**；
  - 记忆的价值要在"必须从历史学到做法"的任务上才显现；本任务集里的目标，
    LLM 靠工具描述与 DSL 参考就能解决，不需要历史。
  - 规则臂的记忆对照更是结构上无效：它的技能是**写死的脚本**，
    有没有记忆都走同一条路（实测六项指标完全相同）。

> **一个测不出差异的评测，不等于「没有差异」的证据。** 这条纪律写在这里，
> 也写进了 `harness.py::default_arms` 的注释——避免今后拿"指标一样"当成结论。

## 2.9 框架版 vs 手写最小 loop（`nolib/`）

回答"自己写的怎么跟成熟框架比"。为了隔离变量，nolib **复用同一批节点函数、同一个
工具注册表、同一个模型**，只把编排层换成手写的 `while` + `_merge`。

运行：`tcms-agent nolib --verify`

### 一、编排层代码量（运行时实测，非手抄）

| | 有效行 |
|---|---|
| `nolib/loop.py`（自己实现编排） | 175 |
| `graph.py`（图装配） | **121** |
| `runner.py`（checkpoint / 审批驱动 / 回放 / 日志） | 210 |
| `nodes.py`（**两版共用**，与框架无关） | 617 |

### 二、同集实测：**结果完全一致**

```
任务 11 条：graph 91% / nolib 91%
平均步数 4.82 / 4.82；平均工具调用 3.82 / 3.82
逐条一致（11/11）
```

**这是本对照最重要的结论：框架不参与决策，因此不改变任务结果。**
决策在节点里，而节点两版共用——换编排层不改变任何一条任务的成败。

### 三、能力差异（8 项断言全部通过，`--verify` 可复跑）

| 能力 | graph | nolib | 证据 |
|---|---|---|---|
| 任务结果 / 工具体系 | ✅ | ✅ | 同集逐条一致；共用同一个 ToolRegistry |
| 状态落盘 | ✅ | ❌ | graph 写 checkpoint 表；nolib 不写任何库 |
| 断点续跑 | ✅ | ❌ | graph `history()` 逐超级步快照 |
| **人工审批中断** | ✅ 暂停等人 | ❌ 自动拒绝 | graph `interrupt/resume`；nolib 无挂起能力 |
| 轨迹回放 | ✅ | ❌ | graph `get_state_history` |
| 流式观测 | ✅ | ❌ | graph `stream()`；nolib 跑完才见结果 |

**nolib 的缺失是被如实披露的**：需审批的调用会当场拒绝、写进轨迹、且**真的什么都没写**
（测试 `test_nolib_auto_rejects_approval_and_never_silently_writes` 验证了文件系统状态）。

### 四、这段对照真正教给我的

框架版的编排代码**并不比手写短**（121 vs 175 只算编排；加上 runner 的 210 行就更多）。
它买到的是**能力**，不是行数：

- 为 R3b 的 human-in-the-loop 付出的最大代价，不是写审批逻辑，而是搞清
  **"被中断的节点会从头重跑，副作用必须放在 `interrupt()` 之后"**——
  当时用最小实验实测才确认（`prep` 执行 2 次、`after-resume` 执行 1 次）。
  这类"状态机必须可序列化、可挂起、可恢复"的坑，手写要吃很多次亏。
- 所以正确的问法不是"自研还是框架"，而是**"哪些能力值得买"**：
  编排、持久化、中断、回放值得买；工具设计、记忆策略、评测门禁、领域整合
  必须自己造（`nodes.py` 617 行、`tools/` 全套、`memory/`、`eval/` 都是自研）。

## 2.10 白盒：运行中就把真实步骤摊开（platform 侧）

### 问题

平台此前在 Agent 运行期间只显示一句**硬编码轮换文案**（"正在检索证据…"），
真实轨迹要等跑完才逐条揭示。这不是"不够好看"，而是**另一类不诚实**：
它声称的步骤与实际发生的事没有关系（可能显示"正在评审结果"而实际还在检索）。
在一个以"机器自证、可审计"为卖点的项目里，用假进度展示"透明"是自相矛盾的。
详见 ADR-019。

### 做法

**后端**：`TaskRun.log(step, detail, payload)` 现在多带一份**结构化载荷**——
这才是白盒的"料"，前端的呈现方式在它之后才决定成败：

| 步骤 | 载荷里有什么（可核对的事实，不是转述） |
|---|---|
| `plan` | 目标故障、期望处置、检索问句、场景池大小 |
| `retrieve` | **真实查询串**、命中逐条（doc_id / 分数 / 通道 / 出处）、域路由来源与域 |
| `act` | 决策后端、**完整候选集**（含"注入几个故障"）与选中标记、策略原文 |
| `exec` | 场景文件、**该场景实际注入了哪些故障**（键 / 等级 / 期望 / 现象 / 时刻） |
| `verify` | 断言逐条 expect→actual→passed |

**SSE 端点** `GET /api/agent/run/stream`：每产生一条真实轨迹就推一条，
末尾给出与 `POST /api/agent/run` **同构**的完整报告（`harness.summarize_runs` 被
两个端点共用），因此前端**不需要把任务跑第二遍**——那会多花一次真实引擎执行
与一次模型调用。

**前端**：`LiveWhiteBox` 逐条渲染真实步骤，每步可展开看人话摘要与原始 JSON。
对于**不开流**的路径（自由目标 / 组合 / 诊断走普通 POST），
如实显示"请求处理中…（这条路径不提供逐步轨迹）"，**不借用白盒的措辞**。

### 实测（`T-DOOR` 的真实流）

```
[start]  任务 ['T-DOOR'] 共 1 条
[trace]  plan      任务: 验证车门故障联锁
[trace]  retrieve  知识底座命中 8 条证据      payload: query='车门故障 不能发车 联锁'
[trace]  act       计划: [LLM deepseek-v4-pro-0813] …  payload: 候选 2 个, 选中=door_cascade.yaml
[trace]  exec      真实执行 door_cascade.yaml  payload: 该场景注入 2 个故障 -> ['door_fault','overspeed']
[trace]  verify    相关断言 1 条; achieved=True  payload: door_fault expect=derate actual=derate passed=True
[result] 与 POST /api/agent/run 同构的完整报告
```

注意 `exec` 那一行：**"该场景注入 2 个故障"**——用户最容易被问住的地方，
现在运行中就能看见，而不是跑完才知道。

### 多故障注入的解释（`core/scenario_view.py`）

用户点一个故障进动画却看到三个被注入时，需要一句能照读的回答。
全库 **104 个场景里 61 个是多故障**（最多 6 个），所以这是通用机制而非补丁：

- `GET /api/scenarios/{file}/composition` 摊开场景构成：每个 inject 步骤的
  故障键 / 等级 / 期望处置 / 现象 / 时刻，并标出"你点的那个"与"同场景一并注入"；
- 关系判定是**可证明的事实**：场景步骤是扁平序列，数据模型里没有任何表达
  故障间依赖的字段——因此"不是前置条件"这句话有据可依，不是猜测；
- 给出 `oneliner`（一句可直接照读的演示口径）与 `why`（完整解释）；
- **两个数分开说**：`total_injections`（注入次数）与 `total_faults`（不同故障数），
  在"恢复后重发"型场景里两者不等（ADR-020）；
- 一条**全库不变式测试**守住口径：每个场景的构成统计必须与 YAML 步数逐项一致。

## 2.11 前端白盒 + 可选模型（platform 侧，2026-09-18）

### 问题：白盒只做了一半

上一轮（§2.10）把运行过程做成了实时白盒，但只挂在**任务列表**路径上；
用户天天用的是**自由目标**（一句话 → 解析 → 真实执行），它仍是普通 POST，
界面上只有一句"请求处理中…"。用户的反馈一针见血：

> **系统白盒了，前端没白盒，用户看到的还是一个等待动画。**

七条路径白盒了一条，恰好不是用户走的那条。详见 ADR-023。

### 做法

**后端**：`/api/agent/free/stream`（SSE）与任务路径**同构**：

```
{"type":"start","kind":"free","goal":…,"llm":{backend,model,base_url,override}}
{"type":"trace","entry":{step,detail,t,payload}}    ← parse/plan/retrieve/act/exec/verify
{"type":"result","report":{…}}                       ← 与 POST /api/agent/free 同构
{"type":"end"} / {"type":"error"}
```

- 解析结论先推一条 `parse` 轨迹（命中故障/期望处置/置信度/命中依据），
  未锚定时如实推 `no_match`，并把澄清链（现象反查 / 宽泛问法 / KB 候选）
  复用 POST 的同一条实现——**复制一份必然漂移**；
- 时间轴统一到"用户提交那一刻"：解析与执行连续计时，不中途重启；
- 测试钉住四条：骨架同构、与 POST 同构（防漂移）、未锚定不是 `error`、时间戳单调。

**前端**：两栏工作台（控制区 / 舞台）+ `LiveWhiteBox` 时间轴组件：

- 运行中把白盒作为**主视觉**：每步可展开看人话摘要，原始 JSON 折叠在内层；
- 底部状态行显示"距上一条真实步骤 x 秒"——这是事实，**不编造进度条**；
- 头部如实标注**谁在决策**（模型名 / 是否本次指定 / 是否为离线规则臂），来自后端回填；
- 一键导出整条轨迹 JSON（贴问题单/评审）；
- 空态不摆大白卡，而是**预告将要出现的结构**（四步说明）+ 可点示例 + 环境事实。

### 可选模型：只作用于本次运行

- 模型选择器长在运行入口旁，默认"跟随设置（<模型名>）"，可拉取真实模型列表
  （`POST /api/llm/models`，非对话类折叠）、筛选、手动输入；
- 选择随请求参数下发（`model` / `base_url`），**不写回设置**；报告与轨迹如实标注实际使用；
- **配了 key ≠ 能用**：新增 `POST /api/llm/ping` 与「测试连接」按钮，
  真发一次最小请求并**原样回服务端错误**。
  本机实测过一次很坏的情况——环境变量 `NO_PROXY` 里的 `[::1]` 让 httpx 建 URL 就抛错，
  于是平台每次调用都失败、一直静默走规则臂，而界面写着"LLM 已配置"。
  现在请求层会**绕过坏代理解析重试一次**并如实回报（ADR-024）。

### 实测：换模型效果还在不在（8 个内置任务，真实运行）

| 模型 | 达成 | 平均分 | 平均耗时 | 真用 LLM |
|---|---|---|---|---|
| deepseek-v4-pro-0813（原默认） | 8/8 | 90 | 8074ms | 8/8 |
| deepseek-v4.1-flash | 8/8 | 90 | 5230ms | 8/8 |
| qwen-turbo（最轻） | 8/8 | 90 | **3090ms** | 8/8 |

轻量模型**结果一致、快 2.6 倍**：不是它更强，而是体系把模型职责压得很小
（选场景 + 一句理由），结论由引擎断言与引用校验兜住。
**边界**：这批任务是机器可判定的验证类；开放场景（多跳诊断/自由组合/自造用例）
的退化未必被同一套断言挡住，更严格的仪器是 §2.8 的 11 任务评测集。

**首帧主题**：服务端渲染 index.html 时注入 `<html class="theme-x" data-theme="x">`
（权威在服务端设置），前端脚本按 `data-theme → localStorage → 系统偏好` 取值——
否则换浏览器时会先按系统主题画一帧再跳，深↔浅那一下很刺眼。

## 2.12 界面设计系统、层级治理与"版本可自证"（platform/web）

### 设计系统落在哪

- `src/index.css`：语义 token（双主题各自取值，不是反相）+ 组件类（`.panel/.btn/.input/.tag/.th/.td…`）
  + 动效基元 + 层级刻度。**保留类名只换取值**，因此 7 个页面无需逐页改写即整体换语言。
- `src/components/ui.tsx`：唯一收敛点。`Callout`（一句人话在明面、长解释进 details）、
  `Tabs`（真分段控件）、`KV`、`EmptyState(compact/steps)`、`StatCard(tone=neutral)`、`Panel(sub/dense)`。
  纪律：语义色只表示状态；空态要**预告结构 + 给例子 + 说环境**，不是占位。
- `src/components/ErrorBoundary.tsx`：页面级兜底（按路由 key 重置），一个页面崩了不整站白屏。

### 层级与浮层（"冲突"几乎都出在这四类）

| 类别 | 规则 |
|---|---|
| 层级刻度 | `--z-sticky:20 / --z-popover:40 / --z-modal:70 / --z-toast:90`，禁止裸 `z-40/z-50`（有测试守） |
| `overflow-hidden` | 会**裁掉浮层**、让 `sticky` 失效——浮层与粘性表头不要放在带 overflow 裁剪的祖先里 |
| 弹窗三件套 | 锁背景滚动（body + `overscroll-contain`）、Esc 关闭、关闭后恢复原状态 |
| 入口缓存 | 入口 HTML 必须 `no-store`；哈希资源照常长期缓存 |

### 为什么界面要自报版本（ADR-026）

同一台机器上可能同时存在多份能启动的副本（monorepo / 旧仓库 / 发布包），
界面像、默认端口还都是 8000。"打开了旧副本"如果没有任何线索，用户只能得出
"你根本没改"的结论。因此 `/api/system/status` 返回 `web_build`
（从 `index.html` 的产物哈希与派生时间），界面侧栏底部显示
「界面 <构建时间> · <产物哈希>」——一句话确认版本，不必翻目录或问人。

配套：旧仓库 `start.bat` 改为"只提示不启动"的壳（中文提示在 UTF-8 with BOM 的 `.ps1`，
`.bat` 纯 ASCII；否则 cmd 按 OEM 代码页解析会乱码），并可直接拉起新仓库。

## 5. 实测对照：两个臂的真实差异

同一目标「验证超速必须触发降级处置」：

| | 离线规则臂 | LLM 臂 |
|---|---|---|
| 步数 / 工具调用 | 5 步 / 4 次（检索→查字典→真执行→列场景） | **2 步 / 1 次**（直接真执行验证） |
| 策略 | 方法论式：先把语义查清再验证 | **目标导向**：问题就是"引擎怎么说"，那就直接问引擎 |
| 结论形态 | 字典语义 + 引擎验证并列 | 以**引擎断言表**为主证据，并引用归档路径 |

这不是"LLM 更聪明"的空话，而是可复现的行为差异：**规则臂把流程走全，
LLM 臂走捷径**。两者都有价值——规则臂适合回归门禁（确定性强），LLM 臂适合
真实任务（效率高、会挑重点）。R6 的 A/B 评测就建立在这个对照上。
